# velt-customize — operating brief

Turning a Figma design into clean Velt UI customization (comments + notifications, React) via Planner → Builder → Judge.

## The one rule that governs everything
**`guide/` is the first source of truth — but its *silence* is not a verdict.** For any decision — which component, layer, identifier, behavior, data field, how to verify, how to handle a blocker — READ the relevant `guide/` file and apply it. Knowledge lives across: identifiers (`reference/*`), **prop behavior & interactions** (`reference/behaviors.md`), **data fields / events / custom-data** (`reference/data-models.md`), and **what a component is *for*** (`reference/component-definitions.md`). When the guide doesn't cover something or you're unsure, **don't guess, don't hedge, don't declare it impossible** — **verify against ground truth**: Velt Docs MCP / official Velt docs → the live SDK's behavior/types → an empirical test in the running app; then state the verified fact (and ideally feed it back into the guide). Never invent a name (R10); never hack (R0).

## Flow (do not skip preflight or the gate)
0. **Preflight (before anything) — fail fast, fail clear, NO fallback.** Check + print a ✓/⚠/✗ readiness summary with a plain-language fix per item: guide bundled · **Figma MCP reachable + node resolves (Dev Mode)** · **Velt installed in the repo** · **app runs + Velt renders** (capture the default-UI baseline) · **`claude-in-chrome` (Chrome MCP) connected** · **auth** (never enter creds — manual login → pause and ask). **Hard items — must pass, no fallback: guide · Figma MCP · Velt-installed · app+Velt renders · Chrome MCP.** If Figma MCP is down → HALT (do **not** read the design via Chrome screenshots — that fallback degraded a prior run); if Chrome MCP is down → HALT before building. Any ✗ **HALTS with the fix and changes nothing**; translate tool errors into plain language, never dump a raw stack. Only auth/live-app are **deferred** → enforced at the gate (manual-login pause is the one safety exception). Idempotent — fix and re-run.
1. **Plan (read-only) — the Planner is the BRAIN; Step-1 design overview, go DEEP** (see [`build-methodology.md`](../../guide/build-methodology.md) Step 1). Via **Figma MCP**: go through **every frame** and list **all surfaces** (e.g. sidebar AND pin dialog — don't miss one), every element, **every state** (collapsed-default, focused, expanded, hover, selected, resolved, empty, autocomplete, filter-open, options, toast/tooltip), exact tokens, and **export every icon/asset SVG** (`download_assets` — R17 forbids hand-drawing). **Read the host app's existing Velt props** (`visibilityOptions`, `defaultMinimalFilter`, `sortBy`, …) as design intent. Recognize via `component-definitions.md` (intent notes); confirm behavior via `behaviors.md`, data via `data-models.md`. Pick the layer via `02-decision-tree.md` (Q1–Q4 + S1–S8). **Explicitly list what's NOT supported by default** with the plan for each (prop/wireframe · primitives/headless *only if the data model supports it* · event-driven add like a toast/tooltip · genuine gap → document + suggest the closest alternative · hacky → confirm with the user). Output a **complete, decided action plan**, each decision tagged `verified/assumed/unknown→verify`.
2. **Coverage gate — the ONE user input.** Present the matrix + recommendation and ask **only** which approach to implement. After this, do **not** stop for the user again.
3. **Build → Judge loop — Step-2 methodology, in SMALL PATCHES, AUTONOMOUS to a TRUE match** (see [`build-methodology.md`](../../guide/build-methodology.md) Step 2; read [`build-gotchas.md`](../../guide/build-gotchas.md)):
   - **Builder** (maker): one surface at a time (dialog first). Build the **structure** so it renders, then **style element by element in small patches, each made pixel-perfect before the next** — the loop: render → **inspect the LIVE node** (not the 0-size registry copy) → find the real Velt class → **override with `!important`** → compare to the Figma frame → next. Prefer the native slot + CSS before a custom variant (P4/R12). Use the design's exported icon SVGs (R17; slots like `ToggleReply`/`CopyLink` overwrite inner markup → inject icons via CSS `::before`). Then interactivity/states (hover-reveal, active-class, composer expand, hidden scrollbars), then test features functionally, then the next surface, then the unsupported items. Files under `ui-customization/` only (R11/R18); one stylesheet (R8); one `<VeltWireframe>` (R1). Smoke-test before handoff.
   - **Judge** (checker, fresh context — never the maker): after **each patch**, a **VISUAL side-by-side of the live screenshot vs the Figma frame, pixel to pixel** — border · radius · background · color · spacing · alignment/position · typography · icon identity · every state. **The screenshot is the verdict; numbers only support it. No clean screenshot → `BLOCKED`, never a pass from computed values** (that false-passed a broken build at "90%"). PASS only if a designer couldn't tell them apart. A non-render → **app-vs-build triage first** (`BLOCKED`, not `FAIL`, when env/auth is the blocker; the Velt auth/`documentsReady` stall needs a 10s+ mount or a fresh tab).
   - **Keep iterating** patch by patch until the Judge truly PASSes. Stuck-detection only aborts a no-progress chain. **Never declare a gap to escape** — exhaust inspect→override→data-driven→full-container first.
4. **Report (only at the very end) — polished + honest.** A clean human-readable summary from `templates/`: per surface **what was done · what's pending · where blocked**, logged assumptions, *verified* gaps, the **required host changes** the user must apply (R18 — tested, reverted, listed), screenshots, code.

## Hard guardrails
- Verify each surface before the next (R15/R16). A goal is never "met" without evidence.
- Never enter credentials; use the app's existing auth/test harness — if manual login is needed, pause and ask.
- Touch only `components/velt/ui-customization/` + the report dir. **Never change the host app's non-Velt UI or default behavior (R18)** — a required host change is applied temporarily, verified, **reverted**, and reported to the user as a manual step, never baked in. No deletes, no config/build changes, no commits unless asked.
- **Exactly ONE blocking user question for the whole run: the approach at the coverage gate.** Recognition ambiguities, retries, escalations → autonomous; log + surface only in the final report. (A hard preflight failure halts with a fix; manual-auth pause is a safety exception.)
- A goal is `met` only on a genuine side-by-side match — never on "structure present" or "looks close". Loop until it truly matches.
- Never declare an SDK gap to escape the loop — exhaust inspect (to the leaf element) → CSS vars + class `!important` → data-driven (user color/config) → full-container wireframe, with evidence, first.

## Verified facts (don't relitigate — full detail in the guide)
One `<VeltWireframe>` per app · container slots drop undeclared children → declare the full tree · `ThreadCard` MUST nest in `Body → Threads` · root wireframe auto-removes shadow, nested-only needs `shadowDom={false}` · CSS variables cross shadow, class CSS doesn't · pin index/number slots are empty → fill via `velt-data` · use `VeltCommentDialog`, never the deprecated `VeltCommentThread`.

## When unsure
Read the guide file. If the guide is silent, **verify against ground truth** (Velt Docs MCP / official docs → live SDK → running app) — don't guess or hedge. Only a capability that is genuinely absent *after that verification* (e.g. a field the data model doesn't store) is an SDK gap (`guide/sdk-gaps-and-blockers.md`) — never a hack, and never a guess.
